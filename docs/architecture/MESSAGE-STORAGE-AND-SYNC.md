# 消息存储与同步模型说明

本文用于梳理现代 IM 系统里常见的 `Timeline` 模型，以及围绕它演进出来的两类核心消息库：

- 消息存储库
- 消息同步库

同时也会说明当前 Dipole 的实现方式、与典型现代 IM 方案的差异，以及如果未来要继续演进，适合怎样推进。

本文同时记录设计方向和当前落地状态。2026-08-26 已完成第一阶段 `User Sync Inbox`，会话内 `seq`、设备游标和 `read_seq` 继续分阶段推进。

## 1. Timeline 模型

在 IM 系统里，`Timeline` 可以理解为一条按顺序追加的消息序列。它通常具备这些特征：

- 每条消息都有顺序标识，例如 `SeqId`
- 新消息总是追加到尾部
- 可以按顺序区间读取，也可以从某个位点之后继续拉取
- 读取方只需要记录自己上次读到哪个位点

从逻辑上说，`Timeline` 很适合抽象消息同步和历史漫游：

- 同步：从某个位点之后继续拉取新消息
- 存储：按某个会话的 Timeline 拉取历史消息

基于这个模型，现代 IM 通常会把消息系统拆成两类库。

## 2. 现代 IM 的两个库

### 2.1 消息存储库

消息存储库负责保存会话的完整历史消息。

它的特点通常是：

- 每个会话对应一个 Timeline
- Timeline 中保存该会话的全部历史消息
- 主要用途是消息漫游、历史翻页、搜索和审计
- 保存周期通常较长，甚至长期保留

从数据视角看，它更像：

- 单聊：`direct:U1:U2`
- 群聊：`group:G1`

也就是一个会话一条 Timeline。

### 2.2 消息同步库

消息同步库负责保存“需要同步给某个接收端”的消息序列。

它的特点通常是：

- 每个接收端对应一个 Timeline
- Timeline 中保存该接收端待同步或可同步的消息
- 主要用途是在线失败补偿、离线同步、多端同步
- 不一定永久保留，通常会配 TTL 或生命周期清理

从数据视角看，它更像：

- `sync:user:U100`
- `sync:user:U200`

也就是一个接收者一条 Timeline。

## 3. 两个库的职责区别

这两个库经常会一起出现，但职责不同。

消息存储库关注的是：

- 某个会话里发生过什么
- 会话历史怎么查
- 消息漫游怎么做

消息同步库关注的是：

- 某个用户还有哪些消息没有同步完
- 某个设备从哪个位点开始补拉
- 在线推送失败后如何统一补偿

相比把所有能力都压在一张消息表上，这种分层的好处是职责更清楚，也更容易分别优化：

- 历史消息查询优化
- 多端同步优化
- 生命周期管理优化

## 4. 写扩散与读扩散

消息同步库最常见的讨论，往往会落到写扩散和读扩散。

### 4.1 读扩散

读扩散的思路是：

- 一条消息只写入一次会话 Timeline
- 接收方在同步时，从各个会话 Timeline 里自己去读

优点：

- 写入成本低

缺点：

- 接收方同步逻辑复杂
- 读放大会很明显
- 会产生很多无效查询

### 4.2 写扩散

写扩散的思路是：

- 一条消息除了写入会话 Timeline
- 还要额外写入每个接收者自己的同步 Timeline

优点：

- 接收端同步逻辑简单
- 更适合多端同步
- 更容易做统一补拉

缺点：

- 写放大明显
- 大群场景尤其重

因此现代 IM 常见的策略是：

- 普通单聊、小群：更接近写扩散
- 大群、超大群：引入读扩散或读写混合

## 5. 我们当前是怎么做的

Dipole 已经具备“消息存储库”，并在本轮升级中加入第一版独立“消息同步库”。

### 5.1 我们已有的部分：会话消息存储库

当前项目中的 `messages` 表承担的是会话级消息存储。

对应代码：

- [message.go](../../internal/model/message.go)
- [message.go](../../internal/data/mysql/repository/message.go)

当前消息的组织方式是：

- 单聊：`conversation_key = direct:U1:U2`
- 群聊：`conversation_key = group:G1`

查询历史消息时，我们主要就是围绕 `conversation_key` 做 Timeline 读取：

- `ListByConversationKey(...)`
- `ListByConversationKeyAfter(...)`

因此从逻辑上说：

- `messages` 已经是一套会话级 Timeline 存储
- 这部分对应现代 IM 方案里的“消息存储库”

### 5.2 我们当前的同步方式

当前同步链路更接近：

1. 消息先写入 `messages`
2. 在线用户通过 WebSocket 实时接收
3. 重连或离线后，客户端主动拉取补偿消息
4. 热群场景下，服务端发轻量 `notify`，客户端再 `pull`

当前项目里与同步相关的实现主要包括：

- 在线实时推送：WebSocket
- 离线补拉：`ListOfflineByUserUUID(...)`
- 热群补拉：`group.message.notify + GET /messages/group/:group_uuid?after_id=...`

Redis 在这里承担的是：

- presence 在线状态
- 节点间路由辅助
- 热群检测
- 热群消息页缓存
- 限流与会话状态

### 5.3 已落地的部分：User Sync Inbox

当前项目已经新增以用户为中心的 `user_sync_inbox`：

- `sync_seq`：MySQL 全局自增游标，对单个用户保持单调递增，允许存在空洞
- `user_uuid`：同步 Timeline 所属用户
- `message_uuid`：关联消息事实
- `conversation_key`：客户端归并会话使用
- `(user_uuid, message_uuid)`：保证事件重放时幂等
- `(user_uuid, sync_seq)`：支持增量扫描

消息、Inbox 条目和 Outbox 事件在同一个数据库事务中写入。任意一步失败都会整体回滚。

同步读取接口为：

```http
GET /api/v1/sync?after_seq=1002&limit=100
```

响应返回 `items`、`next_seq` 和 `has_more`。客户端成功处理当前页后保存 `next_seq`，下一次从该位置继续拉取。

直聊消息会写入发送方和接收方 Inbox，便于发送方其他设备归并消息。普通群消息按成员写扩散。热群继续使用 `group.message.notify + group timeline pull`，不写成员 Inbox，避免在高频大群上增加第二份成员级写扩散。

原有 `/messages/offline?after_id=` 暂时保留，用于兼容旧客户端和补拉升级前的消息。

## 6. 当前方案的特点

当前方案的优点：

- 实现简单，主链路清晰
- 会话历史和在线投递都已经能跑通
- 热群已经支持 `notify + pull`
- 不需要一开始就维护复杂的接收端状态

当前方案的限制：

- 当前只有用户级 Inbox，还没有设备级持久化游标
- 尚未设置 Inbox TTL，也没有基于设备完成度的安全回收
- 会话历史仍使用 `messages.id`，还没有会话内单调递增 `seq`
- `conversations` 仍保存结果型 `unread_count`，还没有 `read_seq`
- 热群同步需要客户端同时维护群 Timeline 游标

这说明当前方案适合作为中小规模、功能逐步完善阶段的实现方式，但距离更完整的现代 IM 双库模型还有一段。

## 7. 如果未来要改造，应该如何推进

当前不建议直接大改。更稳的做法是按阶段推进。

### 第一阶段：先明确逻辑模型

在设计上先引入“消息同步库”的概念，但暂时不改主链路。

建议先统一抽象出两个概念：

- 会话 Timeline：对应 `messages`
- 接收端 Timeline：未来的 `sync inbox`

这一步的目标是：

- 把存储和同步的职责边界说清楚
- 为后续改造预留模型，不打断现有功能推进

### 第二阶段：先做最小的接收端 Timeline（已完成）

在不推翻现有消息系统的前提下，新增一张或一套逻辑上的同步库，例如：

- `user_sync_inbox`

字段可以先很简单：

- `id`
- `user_uuid`
- `seq_id`
- `message_uuid`
- `conversation_key`
- `created_at`
- `expires_at`

这一步的目标是：

- 为每个用户建立独立的同步 Timeline
- 先服务离线补拉和多端同步
- 不急着替换现有所有读取路径

### 第三阶段：让多端同步优先走同步库（进行中）

在同步库稳定之后，可以逐步把下面这些能力迁到它上面：

- 离线消息补拉
- 多端首次同步
- 重连后的增量同步

此时会形成更清晰的分工：

- `messages`：负责历史漫游
- `user_sync_inbox`：负责待同步消息

### 第四阶段：增加生命周期管理

同步库的一个关键特点是“可回收”。

如果未来不保存服务端精确同步位点，可以先做：

- 固定 TTL，例如 7 天或 30 天

如果未来要更精细，可以继续做：

- 多端位点汇总
- 到期回收
- 按用户/设备的同步完成度控制清理

### 第五阶段：再评估 Redis / MySQL / 其他存储承载方式

这里不建议先入为主。

同步库可以是：

- MySQL
- Redis
- Redis + 持久化落盘
- 专门的 KV / TableStore / 时序型存储

如何选，应该看当时最真实的需求：

- 更偏功能验证：MySQL 足够
- 更偏高频补拉、短生命周期：Redis 很有吸引力
- 更偏海量持久化和高 TPS：再考虑更专门的底层存储

## 8. 为什么现在不立刻改造

第一版 Inbox 已经以兼容方式落地。后续仍按独立阶段推进，因为这些改造会影响客户端协议和数据迁移：

- 会话内 `seq` 与历史游标切换
- 设备级 Cursor
- `read_seq` 与未读计算
- Inbox TTL 和回收水位

相比这些点，引入独立消息同步库属于更偏架构演进的工作。

它值得做，但适合在：

- 主链路已经稳定
- 多端同步诉求更强
- 对接收端级别状态有更明确要求

之后再推进。

## 9. 总结

现代 IM 系统通常会围绕 Timeline 模型，把消息能力拆成两层：

- 消息存储库：按会话存全量历史
- 消息同步库：按接收端存待同步消息

Dipole 当前已经具备前者：

- `messages` 表就是会话级消息存储库

Dipole 当前已经具备后者的第一版：

- `user_sync_inbox` 提供用户级同步 Timeline
- `/api/v1/sync` 提供 `after_seq` 增量读取
- Redis 继续承担在线状态、路由和热群检测，不承载持久同步状态

当前方案已经能支撑：

- 在线实时消息
- 历史消息拉取
- 离线补拉
- 热群 `notify + pull`

下一步按“会话内 Seq → 设备 Cursor → Read Seq → 生命周期回收”的顺序推进，并在整个迁移期保留旧历史与离线接口。
